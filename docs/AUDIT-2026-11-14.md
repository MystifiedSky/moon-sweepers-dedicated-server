# Moon Sweepers project audit

This records the original findings. Current fixes and validation are tracked in [the remediation report](AUDIT-FIXES-2026-11-14.md); the original observations below are preserved for reference.

Audit date: November 14, 2026. Scope: the current working tree, including untracked project files, the Rust manager and browser, C# plugin, release packaging, AMP configuration, and the running game's loader log. This supplements the earlier `AUDIT.md`; it does not mark these findings fixed.

The project builds, but it has release-blocking problems in process communication, access-control configuration, recovery, and reconnect behavior. There are **18 findings: 9 P1 and 9 P2**. Seven findings have isolated executable reproductions; the remaining findings follow from the current code paths and need their proposed runtime checks before a fix is considered validated. P1 means fix before relying on the server for persistent multiplayer worlds; P2 means a significant conditional correctness problem.

## Running game

The running process was `F:\SteamLibrary\steamapps\common\Moon Sweepers\MoonSweepers.exe`, PID 18628, launched with `-force-d3d11`. Its current BepInEx log ended with **`0 plugins to load`** and chainloader startup complete. The game's `BepInEx/plugins` directory was empty, and there was no `BepInEx/moon-ds` runtime directory. Therefore this running session did not load this project's MoonDedicated plugin.

The initial Cpp2IL error about metadata version 108 was followed by the MoonSweepers ModEngine patcher successfully generating interop assemblies. That initial error alone is not evidence the patcher failed. Two later Unity interop preload warnings remain, but this audit does not attribute a game failure to them.

No live saves were modified, no mod was installed into the live game, and the game was not restarted. Anonymous server login, real world loading, two-account joining, vehicle persistence, and Joonas synchronization remain unverified. The log observation establishes a deployment blocker, not a successful plugin runtime test.

## Findings

### A01 P1 Relative runtime paths break manager communication

**Sources:** `src/config.rs:259`, `src/config.rs:285`, `src/supervisor.rs:91`, `src/supervisor.rs:131`, `mod/MoonDedicated/Cfg.cs:86`.

Defaults produce `MOON_DS_RUNTIME=data/runtime`, while the game starts with its working directory changed to `game`. The manager watches `<launch directory>/data/runtime`; the real plugin uses `<launch directory>/game/data/runtime`. Heartbeats and save/stop commands miss each other. The `-logFile` path has the same mismatch. On Linux the default Wine prefix is also relative, although Wine expects an absolute prefix. AMP's relative data directory has this problem when AMP's working directory and the game directory differ.

**Evidence:** `reproduces_runtime_directory_changes_with_child_working_directory` passes against actual Settings code. The fake game does not change working directory, which explains why the existing self-test misses this.

**Fix:** resolve game, data, backup, Wine-prefix, runtime, and log paths against one explicit base before spawning. Test a real child with a different working directory and a path containing spaces.

### A02 P1 A missing explicit config silently removes access controls

**Source:** `src/config.rs:332`, especially `if file.exists()` at line 363.

`--config missing.properties` succeeds with defaults. A typo, missing mount, or deployment error can start a server without the intended password, allow-list, mod policy, ports, or save slot. Missing an explicitly selected file should be fatal, even if an absent optional default file is allowed.

**Evidence:** `reproduces_explicit_missing_config_silently_disables_access_controls` confirms successful loading with password and allow-list disabled in this audit environment.

**Fix:** distinguish an explicit CLI/environment selection from the optional default. Reject unknown setting names as well, so typos cannot silently disable intended restrictions.

### A03 P1 Restore modifies the world before validating the archive

**Source:** `src/backup.rs:95`.

Restore deletes the previous `.before-restore` directory and moves the current world aside before reading entry contents or checking their CRCs. If extraction fails, the active save directory is empty or partial. The immediately preceding world survives in the new aside directory, but the older recovery copy has already been deleted. An empty unrelated ZIP is also accepted as a successful restore because there is no save manifest or content validation.

**Evidence:** `reproduces_restore_failure_replaces_world_and_deletes_previous_recovery` creates a valid ZIP directory with corrupt entry data. Restore returns an error after moving the current world aside and deleting the previous recovery copy.

**Fix:** extract into a sibling staging directory, validate CRCs, expected save contents and size limits, then swap directories. Keep uniquely named recovery copies and roll back a failed swap. Stream extraction rather than allocating each full entry in memory.

### A04 P1 Backup retention deletes unrelated archives

**Sources:** `src/backup.rs:69`, `src/backup.rs:73`, `src/backup.rs:81`.

Retention considers every `.zip` in the configured backup directory, regardless of ownership or save slot. A new backup with keep=1 can delete a user's unrelated archive or another slot's backup. It also sorts `...-2.zip` before `....zip`, so a second backup in the same second can immediately delete itself and leave the older backup. `create()` still returns success with a path that no longer exists. Numeric suffixes introduce further ordering problems at double digits.

**Evidence:** `reproduces_pruning_deletes_unrelated_zip` confirms that creating a slot-1 backup removes `aaa-unrelated.zip`. `reproduces_same_second_backup_prunes_the_backup_it_just_created` confirms successful creation returning a deleted backup path.

**Fix:** restrict retention to an explicit application-owned naming scheme and chosen retention scope. Sort by recorded creation time with a stable numeric sequence. Preserve unknown files.

### A05 P1 Heartbeat freshness is not a process lock

**Sources:** `src/supervisor.rs:70`, `src/main.rs:255`.

Two managers can both pass `prepare()` before either child writes a heartbeat. A frozen live game with a heartbeat older than 15 seconds also passes the startup and restore checks. The second manager can delete commands while the first process still runs; restore can move files underneath a live game. Conversely, a cleanly stopped server's fresh state rejects a legitimate immediate restart for up to 15 seconds.

**Evidence:** source control flow; no exclusive lock is acquired. The check is performed only before the spawn loop and is based entirely on JSON time.

**Fix:** hold an OS-backed exclusive lock for the server lifetime and use that same lock for restore. Establish an instance/session ID for status files. Validate simultaneous startup, frozen heartbeat, and immediate restart.

### A06 P1 Rejoining the same roster leaves the game member list empty

**Sources:** `mod/MoonDedicated/PlayerClient.cs:103`, `:165`, `:237`.

Disconnect clears the game's member list, but neither disconnect nor the next request resets `publishedHash`. Rejoining the same server with the same players and names computes the same hash, so `Publish()` skips `Game.AddMember` and the change event. The plugin sets `connected=true` while the game's roster remains empty. The server has an analogous cache risk after `Game.ClearLobbyState()` on Steam disconnection.

**Evidence:** source state transitions; no game session was available to reproduce the gameplay symptom.

**Fix:** invalidate the cached hash and roster on every reset, or make initial roster publication unconditional for each connection generation. Test join, leave, and rejoin without restarting the game.

### A07 P2 Concurrent authentication can exceed the player limit

**Sources:** `mod/MoonDedicated/DedicatedServer.cs:321`, `:407`.

Capacity counts only already-authenticated peers when a ticket is submitted. With one slot left, two pending players both pass; the later validation callbacks mark both authenticated without another capacity check. Pending peers also have no independent fixed authentication deadline: ping updates `Heard`, while `Since` is never used for expiration.

**Fix:** reserve bounded pending slots or enforce capacity again before admission. Apply an absolute authentication deadline and bound pending sessions. Test simultaneous validation with max_players=1.

### A08 P1 External stop is treated as a crash and may restart

**Sources:** `src/main.rs:186`, `src/supervisor.rs:176`, `:208`.

`moon-ds send stop` writes directly to the plugin queue, leaving the supervisor's `stopping` flag unset. When the child exits normally, the manager calls it an unexpected exit. With auto-restart enabled it starts another server; without it, it returns the crash exit code. The graceful-stop backup path is also skipped for that exit.

**Evidence:** `checks/audit-2026-11-14/runtime_reproduction.py` ran the actual manager against its fake child with auto_restart=1. Output reported `game exited unexpectedly (code 0)` followed by `restarting (1/1)`. The test then stopped the manager through stdin. Logs are in `runtime-result.json`.

**Fix:** route external administrative commands through the supervisor, or recognize an explicit per-session shutdown acknowledgment and suppress restart. Test stdin stop, external stop, Ctrl+C, and actual crashes separately.

### A09 P1 Standalone backup does not coordinate with saving

**Sources:** `src/main.rs:222`, `src/supervisor.rs:288`, `src/backup.rs:38`, `mod/MoonDedicated/DedicatedServer.cs:626`.

The console `backup` command requests a save and waits. The separate `moon-ds backup` command immediately zips live files. It can combine files from different save revisions. The ZIP builder silently skips any file it cannot open, including permission/sharing failures, and still reports success. `moon-ds send backup` is not equivalent either: it reaches the plugin, which has no backup command.

**Fix:** expose one coordinated backup operation. Obtain a save acknowledgment and prevent file mutation during the snapshot, or back up an immutable completed generation. Treat unexpected missing/unreadable files as an incomplete backup. Test all documented command entry points.

### A10 P2 Failed saves and forced termination can report clean shutdown

**Sources:** `src/supervisor.rs:208`, `:314`, `:347`; `mod/MoonDedicated/DedicatedServer.cs:592`, `:617`.

A child exit while `stopping` is set produces `Outcome::Stopped` regardless of exit code or final save success. The stop-timeout branch kills the game and also returns `Outcome::Stopped`. The outer loop returns zero. A save failure may print a warning, but automation receives a clean result; the timeout branch additionally skips `after_stop()`.

**Fix:** carry explicit saved, save-failed, forced, and crashed shutdown outcomes through to the exit code and backup policy. Test a faulted save task, child crash during shutdown, and timeout.

### A11 P1 Failed native hooks leave a partially active plugin

**Sources:** `mod/MoonDedicated/Hooks.cs:39`, `mod/MoonDedicated/DedicatedServer.cs:48`, `mod/MoonDedicated/PlayerClient.cs:43`, `mod/MoonDedicated/Plugin.cs:25`.

Hook failures return null while retaining hooks that already succeeded. The dedicated server logs the failure count and still returns success; the player installer always reports ready. Plugin.Load ignores Install's return value. Client replacements call original delegates without null checks, and `origUpdate` is invoked outside the exception handler. If trampoline generation fails after a detour is installed, execution can reach a replacement with no original delegate.

**Fix:** validate required methods and signatures before mutation, track installed hooks, and roll back the entire installation if any required hook fails. Treat optional hooks separately. Fail-injection tests should verify normal game functions remain callable after rollback.

### A12 P2 Failed world joining is reported as success and never retried

**Sources:** `mod/MoonDedicated/PlayerClient.cs:255`, `mod/MoonDedicated/Il2.cs:187`.

`Il2.Invoke` converts a managed exception into a log and zero return. `BeginJoin()` ignores that failure, sets `joinStarted=true`, and writes a successful join result. The tick loop never calls it again while that flag is set. The same issue applies to a failed join constructor. A roster heartbeat can continue indefinitely while the player remains in the menu.

**Fix:** return an explicit invocation success/error result, and observe world-download completion or failure with a deadline. Set the attempt flag only after a successful invocation and provide a bounded retry or a clear disconnect result.

### A13 P2 Importing into a descendant recursively copies itself

**Source:** `src/import.rs:24`.

`copy_tree` creates the destination and then enumerates the source without checking their relationship. Importing a game into `<source>/server-copy` traverses the newly created destination and creates `server-copy/server-copy/...` until a path or storage failure. Directory links can introduce similar cycles. Import also copies BepInEx runtime JSON, including pending connection requests and stale state, because the skip list excludes only selected folders and `.log` files.

**Fix:** canonicalize and reject equal/descendant destinations, explicitly handle directory links, and exclude transient mod state. Test the ancestry guard before doing any recursive copy.

### A14 P2 Version checks compare constants rather than the actual game

**Sources:** `mod/MoonDedicated/Cfg.cs:45`, `mod/MoonDedicated/PlayerClient.cs:148`, `mod/MoonDedicated/DedicatedServer.cs:412`, `mod/MoonDedicated/Game.cs:34`.

Both sides advertise the compile-time string `1.0.5`. Neither reads the running game version or checks the executable/metadata identity. An updated game retaining the expected method names still passes resolution and reports itself as 1.0.5, even if layouts or behavior changed. This contradicts the documentation's claim that a game update causes refusal rather than guessing.

**Fix:** validate an actual game build identifier or supported artifact fingerprint before installing hooks. Use exact signature validation for native targets. Test a mismatched build independently of renamed-method detection.

### A15 P2 Save timeout permits overlapping saves

**Source:** `mod/MoonDedicated/DedicatedServer.cs:592`.

After 90 seconds, SaveTick frees the task handle and sets `saveTask=0` without canceling or confirming completion of the underlying task. A later manual or automatic save can start a second save while the original still writes. During shutdown, the same timeout immediately permits quitting with a save still active. The risk occurs on slow or stuck storage; it has not been observed with the live game.

**Fix:** distinguish timed-out from completed tasks, prevent additional saves until the original completes or is safely canceled, and surface the condition to the manager. Validate with an intentionally delayed task.

### A16 P2 Query reassembly mixes unrelated UDP replies

**Source:** `src/a2s.rs:151`, particularly the split-packet branch at line 166.

The reassembler reads a reply ID but uses it only to check compression. It combines fragments by their fragment number, overwrites the expected total with each packet, and does not check that indexes are within range. Fragments from different replies on the same server socket can become one accepted response. The browser can show a fabricated mixture of names, rules, or required mods, or reject a valid response after packet interleaving.

**Evidence:** `reproduces_query_combines_fragments_from_different_reply_ids` supplies fragment 0 with reply ID 100 and fragment 1 with reply ID 200. The actual query client accepts the combined rules as `moon_mods=evil@1`. This is a parser-correctness reproduction, not a demonstration that an arbitrary third-party sender can bypass the connected UDP socket's peer filtering.

**Fix:** group fragments by reply ID, enforce consistent total/packet size, validate indexes, and require every expected fragment before parsing. Bound accumulated bytes and retain the overall timeout.

### A17 P2 The encoder can generate login packets the receiver rejects

**Sources:** `mod/MoonDedicated/Protocol.cs:43`, `:76`; `mod/MoonDedicated/PlayerClient.cs:144`.

The decoder limits frames to 16,384 payload bytes, but Frame and Encode impose no aggregate payload limit. The client sends its entire plugin inventory. A large inventory that stays within the decoder's 256-mod count limit can exceed the frame limit, be silently discarded, and be retried until the player sees a misleading server timeout. A large missing-mod rejection can similarly exceed the allowed frame size.

**Evidence:** the isolated C# harness links the actual Protocol.cs and Cfg.cs. An auth request with 200 mods and a 2,048-byte ticket produces a 19,281-byte frame, which the same parser rejects against its 16,396-byte frame maximum. It also confirms that a final string declaring 100 bytes but containing one byte is accepted by DecodeAuth, because BinaryReader.ReadBytes permits short reads. The latter is parser-hardening debt rather than a separately demonstrated authentication bypass.

**Fix:** define and validate shared per-field, count, and aggregate wire limits before sending. Return a clear local inventory-size error or introduce bounded protocol fragmentation. Make decoders require exact field lengths and complete payload consumption.

### A18 P2 The browser blocks joins even when mod policy is off

**Sources:** `src/gui.rs:252`, `src/client.rs:163`, `mod/MoonDedicated/Mods.cs:48`, `mod/MoonDedicated/DedicatedServer.cs:513`.

The server publishes both `moon_policy` and `moon_mods`. With policy=off, server-side Mods.Check permits players regardless of that list. The browser unconditionally treats `moon_mods` as required and prevents joining when any listed mod is absent or the wrong version; it never consults the policy. Thus switching enforcement off on a configured server does not let affected players join through the supported browser.

**Fix:** use the advertised policy consistently. Treat the list as informational when enforcement is off, check required entries for required policy, and explain extra-plugin restrictions for strict policy. Test policy changes against the same advertised mod list.

## Remaining runtime checks

1. Load MoonDedicated in a disposable prepared game copy. Confirm successful type resolution and all required hooks before starting a world. The currently open game cannot supply that evidence because this plugin was not loaded.
2. Exercise roster object construction and native hook signatures in the actual plugin. A suspected reference-pointer convention problem was not established: upstream's [field accessor generator](https://github.com/BepInEx/Il2CppInterop/blob/master/Il2CppInterop.Generator/Utils/FieldAccessorGenerator.cs) and [object-to-pointer emitter](https://github.com/BepInEx/Il2CppInterop/blob/master/Il2CppInterop.Generator/Extensions/ILGeneratorEx.cs) pass direct object pointers to static reference setters, consistent with this project's approach. Do not change these calls based solely on the generic `void*` declaration.
3. Use two licensed accounts to test anonymous server authentication, wrong passwords, rejected mods, capacity races, kick, timeout, reconnect, and Steam loss/recovery. Verify unauthenticated traffic on channels 0–2 cannot mutate the world; this source audit does not establish a bypass.
4. Compare vehicle/world state across leave, reconnect, successful stop, and forced stop. Check actual save contents and restored playability, rather than only task completion and ZIP existence.
5. Exercise Wine/Xvfb and AMP on Linux. No Linux runtime or AMP instance was tested here. AMP's Steam-download route does not itself install BepInEx or the required patcher, and its prepare stage allows failure, so a clean download is not a ready server installation.

Address A01–A05 before running a persistent public world, then fix hook installation and reconnect behavior before multiplayer acceptance testing. Keep the existing separate-Windows-user guidance: `data_dir` does not isolate Unity's persistent save location.
